# Git & GitHub 학습 정리 및 직관적 개념 요약

## 1. Git / GitHub 개념
- **Git & GitHub를 사용해야 하는 이유**: 코드의 변경 이력을 시간 순으로 안전하게 추적할 수 있으며, 팀원들과 협업 시 코드 충돌을 방지하고 작업 내용을 명확히 관리하기 위해 사용합니다.
- **Git vs GitHub**:
  - **Git**: 내 컴퓨터(로컬)에서 소스 코드 버전을 관리해 주는 도구.
  - **GitHub**: Git으로 관리한 기록을 클라우드에 올려 공유하고 협업할 수 있게 해주는 웹 서비스.
- **Repository**: 프로젝트 파일과 커밋 이력이 저장되는 저장소.
- **Commit**: 작업한 변경 사항을 스냅샷으로 기록하는 행위.
- **Branch**: 기존 코드 흐름을 해치지 않고 독립적으로 새로운 기능을 개발하기 위해 나눈 가지(포인터).
  - *비유*: 프로젝트 폴더를 통째로 복사하는 것이 아니라, 하나의 연결된 필름(커밋 히스토리) 위에서 카메라/영사기 위치(HEAD 포인터)만 이동시켜 내 모니터에 보여주는 화면을 바꾸는 개념입니다.

## 2. git 기본 명령어 및 트러블슈팅
- `git config`: 사용자 정보(이름, 이메일) 설정.
- `git init`: 현재 폴더를 Git 저장소로 초기화.
- `git status`: 파일의 변경 및 스테이징 상태 확인.
- `git add`: 수정한 파일을 커밋 대기 상태(Staging Area)로 올림.
- `git commit`: Staging Area의 파일들을 하나의 커밋으로 기록.
- `git push`: 로컬 저장소의 커밋 이력을 원격 저장소(GitHub)로 업로드.
- `git pull`: 원격 저장소의 변경 사항을 가져와 로컬에 병합.

### 💡 실습 중 겪은 트러블슈팅 경험
1. **`git log` 조회 후 터미널 입력이 안 되는 현상 (`:(END)` 상태)**:
   - Less 에디터 화면에 갇힌 상태이므로, 키보드 **`q`**를 눌러 빠져나온 뒤 명령어를 입력해야 함.
2. **브랜치 전환 시 에러 (`error: Your local changes...`)**:
   - 파일 수정 후 커밋을 하지 않은 상태에서 브랜치를 바꾸려고 하면 Git이 작업 손실을 막기 위해 이동을 차단함. `git add` & `git commit`을 완료하거나 `git stash`로 임시 저장 후 이동해야 함.

## 3. Branch 관리 및 병합 (Merge)

- **git branch 명령어**: 브랜치 생성, 조회, 삭제.
- **브랜치 전략 (main, develop, feature, hotfix, release)**: 목적에 맞게 브랜치를 분리하여 안전하게 협업하는 전략.

### 병합 방식 비교 (Fast-forward vs 3-way merge)

| 구분 | **Fast-forward (빨리감기)** | **3-way Merge ** |
| :--- | :--- | :--- |
| **상황** | 분기 후 `main` 브랜치에 아무 변화가 없을 때 | 분기 후 양쪽 브랜치 모두 새 커밋이 생겨 역사가 갈라졌을 때 |
| **동작** | 별도 커밋 없이 `main` 포인터(책갈피)만 최신 커밋으로 이동 | 두 변경 사항을 통합하여 **새로운 '병합 커밋(Merge Commit)'**을 생성 |
| **비유** | 읽던 책의 책갈피를 앞으로 슥 옮기는 것 | 갈라진 두 역사를 합쳐 새로운 합체 커밋을 올리는 것 |

### Merge Conflict (충돌)
- **발생 원인**: 두 브랜치에서 같은 파일의 **동일한 위치(줄)**를 서로 다르게 수정하고 병합을 시도할 때 발생.
- **특징 및 해결**:
  - 과거 브랜치 각각의 기록과 본질은 커밋 히스토리에 그대로 보존됩니다.
  - 사람이 직접 충돌 난 코드를 선택/수정한 뒤 `git add` 및 `git commit`을 진행하면, 갈등을 해결한 **새로운 병합 커밋**이 꼭대기에 추가되면서 완료됩니다.
